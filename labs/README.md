# labs/

Demo labs for `kiyooo` — self-contained, offline, resettable environments
meant to prove the tool works against something closer to a real
environment than a unit-test fixture. All three live under this one
folder; nothing here lives anywhere else in the repo.

## Reviewer quick look — one port, no sudo, ~10 seconds to load

If you're just here to see whether this works, you need exactly one
command and one port, nothing else:

```bash
.venv/bin/python -m uvicorn app.main:app --app-dir labs/kiyoo-range --host 0.0.0.0 --port 9900
```

Open **http://localhost:9900**. That's [`kiyoo-range`](kiyoo-range/README.md)
— a page per category, all 23 kiyooo ships, each with a "fetch live
evidence" button. No `/etc/hosts` edit, no other lab, no Docker, no other
port. Click any card:

- 4 categories (`exposed-devops-console`, `subdomain-takeover`,
  `known-exploited-cve`, `shadow-saas-tenant`) are fully self-contained —
  the evidence you see is live, generated by `kiyoo-range` itself.
- The other 19 need `labs/kiyoo-ai` or `labs/acmecorp` running to fetch
  *live* evidence — without them up, the button shows a clearly-labeled
  **OFFLINE PREVIEW**: a real, previously-captured example of what that
  category actually returns, not a bare connection error. Every category
  still shows something concrete either way.

This is genuinely the whole "does this work" answer for a walk-by look.
Nothing below this section is required reading unless you want to run a
real scan against planted assets.

## Going deeper — a real scan against live planted assets

**One command starts everything:** `kiyoo-labs` (install once: `ln -sf
"$(pwd)/scripts/kiyoo-labs" ~/.local/bin/kiyoo-labs`). It adds every
`/etc/hosts` entry every lab needs, starts them all (Docker Compose,
~30 ports total across both backing labs), and opens the same
`kiyoo-range` front door — except now its live-evidence buttons hit real
running services instead of showing offline previews.
`kiyoo-labs ai` / `kiyoo-labs acmecorp` / `kiyoo-labs range` starts
just one; `kiyoo-labs stop` / `kiyoo-labs status` cover everything.

| Lab | What it exercises | Start just this one |
|---|---|---|
| [`acmecorp/`](acmecorp/README.md) | Conventional attack surface: exposed DB, leaked secrets, expired cert, SSO false-positive, WAF-reduced severity, seeded-data downgrade | `kiyoo-labs acmecorp` |
| [`kiyoo-ai/`](kiyoo-ai/README.md) | AI attack surface (Stage 11b): MCP twin servers (harmless/dangerous/poisoned), vector store, model registry, notebook server, shadow AI SaaS tenant, plus a drift scenario | `kiyoo-labs ai` |
| [`kiyoo-range/`](kiyoo-range/README.md) | Not a planted-asset lab itself — the interactive front end onto both of the above, plus 4 categories (`exposed-devops-console`, `subdomain-takeover`, `known-exploited-cve`, `shadow-saas-tenant`) that had no home anywhere before it existed | `kiyoo-labs range` |

Each lab is still self-contained under its own folder: its own
`README.md`, compose file (or, for `kiyoo-range`, a plain host process —
see its README), and any app code it needs. `kiyoo-labs` is a thin
orchestrator on top — it doesn't own any lab-specific logic, so a lab's
own README is still the source of truth for what it does.

[`dashboard.html`](dashboard.html) still exists as a plain static
sitemap if you just want the raw URL list without the app — `kiyoo-range`
is the one `kiyoo-labs` opens by default.

`labs/scenarios/dev-exposes-prod.sh` is `acmecorp`'s drift scenario
specifically; `kiyoo-ai` has its own equivalent under
`labs/kiyoo-ai/scenarios/`.

## Adding a new lab

Give it its own folder here (`labs/<name>/`) with its own README, compose
file, and app code — don't add services to an existing lab's compose file
for an unrelated scenario. Update the table above in the same change.
